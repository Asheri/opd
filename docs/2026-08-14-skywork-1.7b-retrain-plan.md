## 背景与关键约束（探索结论）

1. **此前 ms_17b 健康收敛超参**（服务器实测，必须复用）：
   `lr=3e-5`、`kl_reg_coef=0.5`、`delta_clip=2.0`、`top_k_teacher/student=256`、
   `renormalize_topk_support=true`、`batch_size=8`、`n_steps=200`（step120 最优、step199 过训）、
   `dtype=bf16`、`cache_mode=topk`、`warmup_M=0`（L0）。
2. **HFCausalLM 已有 `generate_batch` 骨架（L2 实现新增，需 GPU 验证）**：
   model_factory.py 现在含 `HFCausalLM.generate_batch`（调 transformers generate）。
   → **Stage1 的 L1 warmup（student_init）与 L2 刷新相位在 HF 路径下理论上可用**，不再是
   此前"只能用 L0"的硬约束。但生成骨架的 padding/mask 未在真实模型验证，稳妥起见：
   - **base 缓存**仍用外部脚本预生成 response（阶段 0.4，稳）；
   - **L2 on-policy refresh** 由训练期刷新相位在线生成（阶段 4，需先 GPU 验证 `generate_batch`）。
3. **JsonLinesDataLoader 要求 prompt+response 都非空**（data.py 跳过空 response 行）。
   Skywork 原始只有 prompt+ground_truth，**必须预生成 response**（base 缓存前置）。
4. **prepare_skywork_math.py 输出 parquet**（DAPO prompt + gt），JsonLinesDataLoader 读 jsonl
   → 需额外 parquet→jsonl + 子集采样 + response 预生成三步。
5. **教师对**：1.7B 用 JustRL-DeepSeek-1.5B（teacher_rl）/ DeepSeek-R1-Distill-Qwen-1.5B
   （teacher_ref），同 R1/Qwen2.5 家族（已下载，服务器 models/ 目录）。
6. **model_kind=hf 跳过 Stage0 RL**，直接用预下载教师对（pipeline.py _stage0_teachers）。
7. **L2 Adaptive Teacher Cache 已实现并闭环**（本轮工作，见
   `docs/superpowers/reports/2026-08-14-adaptive-teacher-cache-implementation.md`）：
   四能力（Disagreement / Health Monitor / Dynamic Ratio / Selective Rollout）+ **双池 feeder
   闭环（refresh 样本真正进训练）** + E0-E6 矩阵 + resume 精确续跑，233 测试全绿。
   → 本计划可把 L0 静态缓存升级为**可选 L2 半在线周期刷新**（阶段 4），用 E0/E5 对照量化贡献。

### 0.3 parquet → jsonl + 50K 子集采样
新脚本 `main/scripts/prepare_skywork_jsonl.py`：
- 读 DAPO parquet，提取 `prompt[0].content`（已是 DAPO 模板文本）+ `ground_truth`
- 随机采样 **50,000 条**（seed=42 可复现）
- 输出 jsonl，每行 `{"prompt": <DAPO文本>, "response": "", "ground_truth": <ans>}`
  （response 暂空，下一步填）
- **校验**：50K 行、prompt 非空、ground_truth 非空

### 0.4 response 预生成（base 缓存前置，L0 语义）
新脚本 `main/scripts/prepare_skywork_responses.py`：
- 加载初始 Qwen3-1.7B（`AutoModelForCausalLM`，bf16，**启用 flash_attn**）
- 对 50K 条 prompt 逐批 `model.generate`（transformers 原生，非 pipeline 内部）：
  - `max_new_tokens=8192`（用户要求，训练 response 长度）
  - `temperature=1.0`、`do_sample=True`（on-policy 初始分布，对齐论文 warmup 语义）
  - `batch_size=2`（8192 长序列下控显存），逐题即时落盘 + resume（复用 eval_aime 的 progressive 模式）
- 把生成的 response 文本写回 jsonl 的 `response` 字段
- **校验**：50K 条 response 非空、平均长度合理（非全截断）
- **⚠️ 时长瓶颈（必须知情）**：50K × 8192 = 4.1e8 token。1.7B bf16+flash 自回归 ~50 tok/s
  → **单卡 ~2275 小时（~95 天）**；2×PRO6000 双卡并行也要 ~24 天。这是**全计划最耗时的一步**，
  远超训练本身。**可行路径**（三选一，参见「规模换算与显存/时间预估」）：
  1. **多卡并行生成**（推荐）：2 卡各半 25K 条，~12 天；可进一步 4 卡 ~6 天；
  2. **降 response 长度**：若接受 2048，50K×2048 = 1.0e8 token → 单卡 ~570 小时（~24 天）；
  3. **降数据量**：25K×8192 → ~12 天单卡。
  （注：原计划"10K×2048 ~1.1 小时"**算错 100 倍**，实际 ~114 小时单卡，此处已修正。）
- **定位**：此步只为 **base 缓存**（Stage1 build）提供初始 response，是 L0 语义。
  **L2 的 on-policy refresh 无需此步**——由训练期刷新相位在线生成（阶段 4）。

### 0.5 数据校验
- jsonl 50,000 条，prompt/response/ground_truth 三字段非空
- 用 Qwen3-1.7B tokenizer 试编码，`max_prompt_len=1024`/`max_response_len=8192` 下截断率 <5%

### 2.4 收敛监控判据（逐 checkpoint 检查 metrics.csv）
| 指标 | 健康范围 | 异常处置 |
|------|---------|---------|
| `E[Δ_T]`（adv_mean） | 单调上升，step120 达 +0.04~0.06 | 若停滞/下降 -> 检查 delta_clip/kl |

## 规模换算与显存/时间预估（50K × 8192，用户要求）

> 用户明确要求数据 50K、`max_response_len=8192`、双卡 FSDP。本节**如实**给出这一规模下的
> 显存与时间，并标出两道硬墙与可行路径。**决策前提**：若任一指标不可接受，需在启动前
> 降规模（见各路径），不要硬跑。

### 指标 1：top-k 缓存显存（60 显存墙）
`TensorTeacherCache` topk 模式实际存 **6 张 `(N,T,K)`**（`cache.py`：`ids`/`ids_sorted` int32 +
`rl_k`/`ref_k`/`delta_k`/`delta_k_sorted` 浮点）。50K×8192 下体积：

| K | 缓存总占用（bf16 浮点 + int32） | 单卡 96GB | 双卡 FSDP 192GB |
|---|---|---|---|
| 256（原计划） | **~1.7 TB** | ❌ | ❌ 完全不可行 |
| 64 | ~420 GB | ❌ | ❌ |
| 32 | ~210 GB | ❌ | ⚠️ 超（需 offload） |
| 16 | ~105 GB | ⚠️ | ✅ 双卡可行 |
| 8 | ~52 GB | ✅ | ✅ |

**结论**：K=256 在 50K×8192 下**不可行**。可行两步：
- **降 K 到 16~32**（双卡），或 **K=8~16**（单卡回退）；K 越小 top-k 支撑覆盖越弱（需监控
  E[Δ_T] 是否仍单调上升）。
- **缓存 mmap 磁盘驻留**（`cache.py` 注释指明"可直接落盘/mmap 跨进程共享"）：50K×8192×K 常驻
  磁盘 + 按 batch 索引加载，GPU 只放 batch 切片。K=32 时磁盘文件 ~210GB，需预算磁盘空间。
- ⚠️ 若不做 mmap、缓存全进 GPU，**5 万 × 8192 的密集/大 K 缓存必然 OOM**。

### 指标 2：response 预生成时长（时间墙）
50K × 8192 = 4.1e8 token，1.7B bf16+flash 自回归 ~50 tok/s：

| 方案 | 时长（单卡） | 时长（2×PRO6000 并行） |
|---|---|---|
| 50K×8192 | ~2275 h（95 天） | ~24 天 |
| 50K×2048 | ~570 h（24 天） | ~6 天 |
| 25K×8192 | ~1140 h（48 天） | ~12 天 |
| 10K×8192 | ~455 h（19 天） | ~5 天 |

**这是全计划最长的一步**，远超训练本体（~1 小时）。建议：**2 卡各半 + 分段 resume**，接受
天级预算；或先降长度/数据量跑通实验，确认收敛再放大。原计划"10K×2048 ~1.1 小时"是算错 100 倍。

### 指标 3：训练本体（非瓶颈）
200 步 × batch=4 × 9216 token(1024+8192) = 7.4e6 token，双卡 ~3k tok/s → **~40-60 分钟**。
单卡 PRO6000 96GB、batch=4、bf16：student+worker+optimizer ≈ 3×1.7B ≈ 10GB，长序列 KV 缓存
大但 batch 小，单卡可行。**双卡 FSDP 主要收益在提速与更大 batch，不是显存刚需**（单卡也够）。

### 指标 4：双卡 FSDP 显存分摊
FSDP 分片（tp_size=1）把参数/梯度/优化器状态按卡分片：1.7B 每卡 ~权重 0.85B + 激活。launch 走
`launch_distributed_scheduler`（ray + NCCL），**骨架未 GPU 验证**，见阶段 2.1 退化冒烟。

## 断点重载验证（防服务器突然关机）

**检查结论**：断点续训**已实现并有测试覆盖**，但需在真实训练前验证一次。

- **checkpoint 落盘**（`checkpoint.py` / pipeline `_save_ckpt`）：每 `checkpoint_every` 步写裸
  state_dict 到 `run_dir/checkpoints/step_<N>.pt`；L2 开启时额外存 optimizer / RNG / ring buffer
  （G8 闭环，`checkpoint.py` 支持 `_opt_state_to_cpu`）。
- **resume**：`--resume` 从最新 checkpoint 恢复 student 权重 + step 计数；L2 路径恢复 optimizer
  与 ring buffer（`RefreshRingBuffer.state_dict/load_state_dict`）。
- **⚠️ 已知边界**：分布式（FSDP）下 `checkpoint.py` 注释标"应改用 `optimizer.get_state_dict()`
  对称恢复"——**双卡 FSDP 的 resume 未验证**，需在阶段 2.1 双卡冒烟里测一次中断恢复。
- **服务器关机防护**：

## 阶段 4：L2 周期刷新增强（推荐）

> **目的**：把 L0 静态缓存升级为 L2 半在线周期刷新，用 on-policy 样本周期 refresh 教师缓存，
> 进一步缓解曝光偏差（L0–L3 曝光偏差谱上比 L1 更高一级）。L2 四能力 + 双池 feeder 闭环
> 已实现（见 `docs/superpowers/reports/2026-08-14-adaptive-teacher-cache-implementation.md`，
> 233 测试全绿），本阶段是**把 L2 接入 Skywork 重训练**，并跑 E0（L0 基线）vs E5（全 L2）对照。

### 4.1 单卡适配（L2 交替相位是单进程；双卡 FSDP 用于 base 训练相位）

L2 交替相位是**单进程**（训练相位 ↔ rollout 刷新相位 ↔ refresh 训练相位分时复用），
**不强制双卡**。双卡 FSDP 的收益在 base 训练相位（更大 batch / 更快），L2 刷新相位本身单卡即够：
- 训练相位：base 池 `_train_step`；双卡 FSDP（`distributed=true`）下走 `DistAsyncScheduler` + NCCL，
  需先过阶段 2.1 双卡冒烟；
- 刷新相位：`run_refresh_phase` 常驻教师对前向 + student `generate_batch` 生成 on-policy response；
- refresh 训练相位：`_train_step_refresh` 从 ring buffer 取 `s_old + Δ_T` 做稀疏 top-K PG+KL；
- **phase 4 建议**：若双卡骨架未验证，E5 也可单卡跑（`distributed=false`），L2 核心价值不依赖双卡。

**显存构成**（pipeline 装配实际驻留）：`student` + `student_ref`（初始副本）+
scheduler hf worker（另一份学生副本）+ `teacher_rl` + `teacher_ref` ≈ **3×1.7B + 2×1.5B ≈
8.2B 参数**，bf16 ≈ **16.4GB**，远低于单卡 96GB，无需 offload。**缓存不常驻 GPU**（见
「规模换算」，50K×8192×K 缓存 mmap 磁盘 + 按 batch 索引）。关键前提是**K 已降到 16~32**，
否则缓存本身爆显存/内存。

**⚠️ 前置（必须先 GPU 验证）**：`HFCausalLM.generate_batch` 是骨架，padding/mask 未在真实模型
验证。刷新相位依赖它，须先跑通 1 条 prompt 的生成（见 §3.3 前的冒烟）。

### 4.2 配置（l2 段参考值，`--set` 注入，不改共享 yaml）

⚠️ **不要把这些 l2 键写进共享 `skywork_17b.yaml`**——阶段 2.2 的 E0（L0）训练用同一 yaml，
写进去会污染基线。正确做法：阶段 4.3 用 `train --set l2.*` 注入（或另存 `skywork_17b_l2.yaml`）。
以下为 E5 完整参考值，已通过本地 `info` 校验（config.py `L2Cfg` schema，`extra="forbid"`）：

```bash
# E5 的 l2 全量覆盖（运行时注入，写进 yaml 的等价物）
--set l2.enabled=true \
--set l2.t_train=100 --set l2.m_refresh=256 \
--set l2.cache.refresh_size=2048 --set l2.cache.max_response_length=8192 \
--set l2.cache.refresh_min_interval=50 --set l2.cache.refresh_max_interval=150 \
--set l2.disagreement.enabled=true --set l2.health_monitor.enabled=true \
--set l2.refresh_ratio.mode=adaptive --set l2.refresh_ratio.initial=0.30 \
--set l2.refresh_ratio.min=0.10 --set l2.refresh_ratio.max=0.60 \
--set l2.selective_rollout.enabled=true --set l2.selective_rollout.candidate_multiplier=4 \
--set l2.selective_rollout.value_fraction=0.80 --set l2.selective_rollout.coverage_fraction=0.20 \
--set l2.selective_rollout.exploration_fraction=0.20 \
--set l2.utility.disagreement_weight=0.5 --set l2.utility.reward_weight=0.3 \
--set l2.utility.age_penalty=0.2
```

> 语义注：
> - `t_train=100` + `n_steps=200` → 2 个相位边界，G4（`refresh_min/max_interval`）下各触发
>   一轮刷新，共 2 轮（冷启动首相位必刷）。
> - l2 的 refresh 训练步是**补充步**，E5 总步数会 >200（不计入 base n_steps 口径）。
> - `disagreement.enabled` / `health_monitor.enabled` 目前是**纯配置开关**：pipeline 恒构造
>   `DisagreementComputer` / `CacheHealthMonitor`（实现报告 §8 已知问题 3），enabled 不 gating
>   计算，仅作 E0-E6 的语义标记。真正 gate 刷新的是 `selective_rollout.enabled`（selector 为
>   None 时刷新相位整体短路，见 4.5 已知问题）。

### 4.3 运行（E0 基线 vs E5 全 L2 对照）

⚠️ **用 `train` 子命令，不用 `experiment`/`run_l2_ablation.py`**：CLI 无 `experiment` 子命令
（cli.py 只有 train/cache/eval/info/eval-aime）；`run_l2_ablation.py`（`scripts/run_l2_ablation.py`）
是 **toy/CPU 演示工具**——它走 `experiment.build_config`，**不加载 skywork yaml** 且注入 toy 默认
（batch=4、max_response_length=4、refresh_size=16），跑的是 CausalToyLM + toy 数据，不是真实
1.7B+Skywork。真实对照用 `train` + `--set l2.*`：

```bash
cd /root/opd/main
# E0 = 纯 L0 基线（复用阶段 2.3 命令，显式 l2.enabled=false；双卡 FSDP 或单卡回退）
torchrun --nproc_per_node=2 --master_port=29500 \
  -m fullstack_opd_v2 train --config configs/skywork_17b.yaml \
  --run-dir /root/autodl-tmp/runs/skywork_17b/e0 \
  --set stage1.load_cache=true --set l2.enabled=false

# E5 = 全 L2 + selective（推荐主跑；4.2 的 l2 全量覆盖 + load_cache）
# ⚠️ L2 交替相位是单进程，E5 用单卡（--device cuda:0）+ distributed=false 更稳
python -m fullstack_opd_v2 train --config configs/skywork_17b.yaml \
  --run-dir /root/autodl-tmp/runs/skywork_17b/e5 --device cuda:0 \
  --set stage1.load_cache=true --set stage2.distributed=false \
  --set l2.enabled=true --set l2.t_train=100 --set l2.m_refresh=256 \
  --set l2.cache.refresh_size=2048 --set l2.cache.max_response_length=8192 \
  --set l2.cache.refresh_min_interval=50 --set l2.cache.refresh_max_interval=150 \
  --set l2.disagreement.enabled=true --set l2.health_monitor.enabled=true \
  --set l2.refresh_ratio.mode=adaptive --set l2.selective_rollout.enabled=true \
  --set l2.selective_rollout.candidate_multiplier=4 --set l2.selective_rollout.value_fraction=0.80 \
  --set l2.selective_rollout.coverage_fraction=0.20 --set l2.selective_rollout.exploration_fraction=0.20
```

> E0/E5 共用同一 `cache_skywork_17b.pt`（load_cache=true）：base 池相同，只有 L2 是否注入不同，
> 对照干净。E0 复跑可复用阶段 2.3 结果（同命令同 run-dir）。E5 单卡（L2 单进程交替相位），
> E0 双卡（base 训练相位双卡有提速）——两者可对比但要注明这一差异。

### 4.4 判据（不只盯 final benchmark）

- **训练质量**：E5 的 E[Δ_T]（`metrics` 的 `adv_mean`）单调上升轨迹应 ≥ E0（L2 不劣于 L0），
  AIME ≥ 或≈ E0。
- **效率比值（L2 价值核心）**：`Performance/Teacher Compute =` 有效 Δ_T 信号 token / 教师前向
  token，`Performance/Rollout Tokens =` 有效训练推进 / rollout 生成 token。
  ⚠️ **当前未实现**（实现报告 §9.5：rollout 相位未显式统计 `teacher_forward_tokens` /
  `rollout_tokens`，现用 `total_s` 作代理）。若要用这两大比值下结论，需先加成本核算模块
  （stat 注入 metrics），否则退而用 `timings.json` 的 `total_s` 对比 E0/E5。
- **判定**：若 E5 用更少教师前向（或相近 total_s）达到 ≥ E0 的 AIME → L2 确立价值，取 E5 为
  最终学生；若 E5 仅略低于 E0 但效率大幅提升 → 记录 trade-off，仍可选 E5 或退 E0。

### 4.5 已知问题（E6 语义缺陷，勿用 E6 下 selective 结论）

`pipeline.py` L2 循环的刷新触发条件是 `elapsed >= refresh_min ... and selector is not None`
（`_run_body`）。因此 **`selective_rollout.enabled=false`（E6）时 selector=None，刷新相位整体
被短路**——E6 实际退化为纯 base 训练，**不是「random rollout」**。若用 E6 论证"random rollout
劣于 selective"，结论不成立（实现报告 §7 的 E6 数字即此退化产物）。本计划只跑 E0/E5，不受影响；
若后续要测 random rollout 对照，需先修该触发条件（refresh 相位不应依赖 selector 存在，仅
选择策略退化为 uniform）。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| **response 预生成耗时长（50K×8192→单卡~95 天）** | **最大风险**：2 卡各半 + 分段 resume；或先降长度/数据量跑通实验再放大（见「规模换算」） |
| **topk 缓存显存（50K×8192 下 K=256→~1.7TB）** | **降 K 到 16~32** + 缓存 mmap 磁盘驻留、按 batch 索引；不 mmap 必然 OOM |
| 初始 student response 质量差（1.7B 未训练） | on-policy 对齐论文；Δ_T 信号来自教师对（与 response 质量弱相关） |
| 过训（step199 跌落） | checkpoint_every=20 + step100/120/140 评估 + 早停 |
| Δ_T 爆炸（Skywork 真实词表） | delta_clip=2.0 + topk 稀疏（K 降后覆盖率下降，需监控 E[Δ_T]） |
| 双卡 FSDP 骨架未 GPU 验证 | 阶段 2.1 先单卡冒烟再双卡冒烟；骨架崩则退单卡（96GB 也够） |
| **服务器突然关机** | **断点重载已实现**（每 20 步 checkpoint + `--resume` + metrics append）；双卡 resume 需 2.1 验证 |
| 单卡训练+评估不能并行 | 训练完再评估（串行） |
| **L2 `generate_batch` 骨架未 GPU 验证** | 阶段 4.1 前置冒烟（1 条 prompt）；不稳则退 L1 方案 A |
| **L2 刷新相位耗教师 compute** | `m_refresh` 远小于 base（256<<50K）+ `refresh_max_interval` 门控；E0/E5 对照量化贡献 |
| **单卡 L2 交替相位显存（teacher 常驻 + student）** | 96GB 充裕（3×1.7B+2×1.5B≈16.4GB）；必要时 hf 教师 `offload_to_cpu` |
| **checkpoint→HF 导出脚本（`export_checkpoint_hf.py`）未写** | 阶段 1 待办新增；否则阶段 3.1 无法评学生 checkpoint（eval-aime 不吃裸 `.pt`） |

1. **数据**：skywork_50k.jsonl 50K 条，prompt/response/ground_truth 非空，token 化合规
